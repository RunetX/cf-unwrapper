# Участие в Развертке

Проекту нужны проверки на разных конфигурациях, небольшие воспроизводимые примеры, улучшения форматов и понятная документация. Начать можно без знания Rust.

## Сообщить результат проверки или ошибку

Создайте [issue](https://github.com/RunetX/cf-unwrapper/issues) и укажите:

1. Коммит cf-unwrapper, ОС, версию платформы, конфигурации и режим совместимости.
2. Команды запуска и ожидаемый результат.
3. Фактический результат: код возврата, счетчики сравнения, текст отказа или небольшой фрагмент diff.
4. Минимальный синтетический пример, если удалось его подготовить.

Успешный прогон тоже полезен. Различайте совпадение XML, совпадение внутренних записей и загрузку собранного файла платформой. `xml-diff` и `import-check` могут завершаться с кодом 0 при различиях: приложите счетчики.

Не публикуйте файлы поставщиков, клиентские выгрузки, рабочие модули, секреты и персональные данные. Удалите чувствительные данные из логов и абсолютные пути. Для воспроизведения сократите случай до синтетического объекта и проверьте, что ошибка сохранилась. Если пока не получается, опишите симптом без вложения закрытых данных.

## Предложить изменение

Для крупной доработки сначала опишите задачу в issue: какой сценарий нужен и как проверить результат. Небольшую правку можно сразу прислать pull request. Используйте свою ветку и fork репозитория.

Нужны Rust stable с `rustfmt` и Python 3.11+. Перед отправкой выполните:

```sh
cargo build --workspace --locked
python tools/check.py
```

В описании PR объясните проблему, новое поведение и способ проверки. К исправлению ошибки формата добавьте небольшой синтетический regression test. Для исправления текста достаточно проверки примеров и ссылок.

## Сохранять гарантии формата

- Неподдерживаемый случай должен давать понятный отказ. При отказах загрузки нельзя создавать или заменять итоговый файл.
- Сохраняйте записи, временные метки, W32/W64 и составную структуру контейнеров.
- Не меняйте байты встроенных ресурсов нормализацией строк: для них действуют правила `-text` в `.gitattributes`.
- `xml::imp::new_external` проверяет одиночное имя до I/O и атомарно резервирует собственный временный каталог. Его имя включает PID и процессный атомарный счетчик; параллельные вызовы не должны делить или повторно использовать каталог. Проверку конкурентности нельзя заменять последовательной.
- Если правило пока известно только по образцам, обозначьте границы применимости. Новый случай за этими границами не должен молча давать неверный результат.

Состав переноса и хеши зафиксированы в `docs/source-inventory.json`, происхождение встроенных ресурсов — в `docs/embedded-assets.md`. Если изменение затрагивает проверяемую аудитом область, разберитесь с соответствующей проверкой `tools/audit.py`, обновите относящиеся к изменению записи и объясните причину. Не отключайте аудит ради прохождения CI.

## Проверить свою конфигурацию

Храните входные файлы, эталоны и результаты в игнорируемом `local/`. Следуйте примерам в [README](README.md). Для проверки загрузки сравнивайте записи с файлом, собранным платформой из того же XML: файл поставщика может использовать другой внутренний формат.

Для дополнительной проверки загрузите собранный файл платформой, выгрузите XML и сравните с таким же кругом для эталона платформы. Сама платформа может менять XML при повторном сохранении, поэтому сравнение только с исходной выгрузкой не всегда локализует ошибку.

В публичный PR включайте код и синтетические тесты, а результат локальной проверки описывайте счетчиками, версиями и методикой.

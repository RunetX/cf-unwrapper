## Windows temporary-name isolation repair (2026-10-31)

The previous temporary path was derived solely from the format RNG. Its seed uses whole seconds and PID, so simultaneous calls within a second repeat the same candidate sequence. Atomic `create_dir` prevented sharing an existing directory, but did not prevent reuse of a path another call had just deleted. A native Windows probe confirmed that a directory marked delete-pending while a sharing handle remains open rejects `create_dir` with `PermissionDenied` / OS error 5; closing the handle immediately allows the same path to be created. The published CI log records this error from `new_external`, without the underlying filesystem operation or handle trace, so it cannot independently establish the exact remote syscall. The old concurrent test also passed 30 local runs; local scheduler/filesystem behavior does not reproduce every runner interleaving.

Temporary names now append a process ID and process-wide atomic sequence to the existing GUID; a repeated timer/GUID therefore cannot reuse another call's candidate. Actual reservation remains atomic, stale-name `AlreadyExists` collisions still select a fresh candidate, ordinary permission errors still fail with the candidate path, validation remains before I/O, and cleanup still targets only the reserved directory. The format UUID generator and public API are unchanged. A fixed-GUID regression synchronizes 32 threads producing 128 names: before the repair it found 1 distinct name instead of 128; after the repair all 128 are distinct. The unchanged public 4-by-32 concurrent regression passed 30 local Windows runs (3,840 external creations), and `python tools/check.py` passed with real Cargo package verification (136 files). These are local repair results, not a claim of a successful remote rerun.
